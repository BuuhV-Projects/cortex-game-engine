# 0025 - Internacionalização (EN + PT) na IDE e no site

**Data:** 2026-05-30
**Status:** aceito

## Contexto

O projeto vinha 100% em português brasileiro — UI da IDE, mensagens
de erro, copy da landing, markdowns da documentação. Isso limita a
audiência ao público lusófono e dificulta contribuições
internacionais via PR.

Restrições e preferências (decididas com o usuário):

- Dois idiomas no MVP: **English** (default) e **Português brasileiro**.
- Default em inglês — alcance internacional na primeira impressão.
- Aplicação tanto no **site institucional** (landing + docs) quanto
  na **IDE Electron**.
- Na IDE, o idioma é escolhido **na primeira execução** via modal
  de welcome. Persiste pra próximos boots.
- Sem biblioteca de i18n externa — 2 idiomas e ~80 strings não
  justificam o peso de `i18next` (+200KB ao bundle) nem a curva de
  aprendizado.

## Decisão

### Sistema comum aos dois alvos

- **Dicionários em JSON** por idioma. Lookup por path
  (`fileTree.no_project`, `hero.title_part1`).
- **Função `t(key, params?)`** sincrona. Sem React/Vue hooks porque
  a IDE e o site são DOM imperativo.
- **Interpolação simples** via `{name}` (`process_exited` →
  `"[process exited: code {code}]"`).
- **Re-render via evento DOM** `CustomEvent('locale-change')`:
  componentes que precisam ouvi-lo reconstroem o shell quando
  disparado.

### Site (`web/`)

- `web/i18n/{en,pt}.json` — strings da landing e da página de docs.
- `web/src/i18n.ts` — `t()`, `getCurrentLocale()`, `setLocale()`,
  `applyTranslations()` (aplica via atributos `data-i18n`,
  `data-i18n-html`, `data-i18n-title`, `data-i18n-description`),
  `setupLanguageToggle()` (botões `[data-lang="en|pt"]`).
- **Persistência** via `localStorage` (`cortex-locale`). Default `en`.
- **Docs em pasta separada por idioma**:
  `web/docs-content/en/` e `web/docs-content/pt/`. Cada
  `docs-content/<locale>/NN-slug.md` vira um doc — slugs sem o
  prefixo numérico.
- `docs.ts` faz `import.meta.glob` dos dois diretórios em
  build-time. Trocar idioma na página de docs rebuilda sidebar e
  re-renderiza o conteúdo via `locale-change`.
- **Toggle `EN | PT`** no header sticky de ambas as páginas.

### IDE (`electron/`)

- `electron/renderer/i18n/{en,pt}.json` — strings de toda a UI.
  Namespaces: `welcome`, `menu`, `fileTree`, `bottomPanel`,
  `projectManager`, `preview`, `chat`.
- `electron/renderer/i18n.ts` — `t()`, `getLocale()`, `setLocale()`,
  `initI18n()` (carrega preferência via IPC), `markWelcomed()`.
- **Persistência** via novo IPC `prefs:get` / `prefs:set` em
  `<userData>/preferences.json`. Vive **fora** do diretório do app,
  então sobrevive a reinstalações.
- **Welcome modal** (`Welcome.ts`) mostrado na primeira execução
  quando `prefs.welcomed !== true`. Default selecionado: `en` (com
  título/subtítulo trocando bilíngue conforme o usuário clica em EN
  ou PT). Persiste idioma + `welcomed: true` ao continuar.
- **Menu nativo** — strings vivem em `MENU_STRINGS` no `main.ts`
  (não no JSON do renderer; o menu é construído no processo main).
  Lido do `preferences.json` antes de `Menu.setApplicationMenu(...)`
  pra evitar flash de inglês no boot quando o usuário tem PT.
  Reconstruído via IPC `menu:rebuild` quando o renderer chama
  `setLocale`.
- **Menu nativo em release vs dev**: `app.isPackaged === true` mostra
  apenas o submenu "Project" com **Generate installer** e
  **Language → English/Português** (radio). Em dev os defaults do
  Electron (File/Edit/View/Window) voltam — DevTools e Reload
  acessíveis pra debug. macOS mantém o `appMenu` em ambos pra que
  Cmd+Q funcione.
- **Troca de idioma pelo menu**: clique nos radios "English" /
  "Português" dispara `menu:change-locale` pro renderer. O renderer
  importa `setLocale` dinamicamente (evita ciclo com o Welcome) e
  chama: persiste em `preferences.json`, reconstrói o menu, dispara
  `locale-change` pros componentes re-renderizarem.
- **Re-render dos componentes**: ao receber `locale-change`, cada
  componente (`FileTree`, `BottomPanel`, `ProjectManager`,
  `Preview`, `Chat`) chama seu próprio `buildShell()`. Estado
  interno (projeto ativo, mensagens, etc.) é preservado porque vive
  em campos da classe, não no DOM.

## Consequências

- **Positivo**: usuário escolhe idioma na primeira vez e nunca mais
  precisa pensar nisso. Trocar depois é opcional (próxima fase: aba
  "Settings" — não entra agora).
- **Positivo**: dois idiomas, zero dep externa. Bundle do site
  cresceu ~6KB (JSON dos textos); o da IDE cresceu marginalmente.
- **Positivo**: o agente IA do chat continua adaptativo — responde
  no idioma da mensagem do usuário, então não precisa de tradução
  específica.
- **Negativo**: cada string nova precisa entrar nos dois JSONs.
  Sem checagem em build-time de que en e pt têm as mesmas chaves —
  aceitamos no MVP. (Futuro: schema/checagem via script.)
- **Negativo**: o agente do chat IA recebe `t(key)` evaluado no
  idioma corrente; se traduzirmos mensagens que aparecem em logs
  consumidos pelo agente, ele pode confundir-se. Por isso o
  `AGENT_SYSTEM_PROMPT` continua em PT (com a regra de "responda no
  idioma do usuário") e mensagens de tool result não passam por
  `t()`.
- **Não traduzido (decisão consciente)**:
  - Comentários de código
  - Mensagens do `AGENT_SYSTEM_PROMPT`
  - READMEs do template (vivem dentro do projeto criado, dev edita)
  - ADRs e CHANGELOG
  - Mensagens de erro vindas de IPCs do main process (raras,
    técnicas)
- **Próximos passos não inclusos**:
  - Aba "Settings" pra trocar idioma sem reinstalar.
  - Detecção automática do locale do SO no welcome (`app.getLocale()`).
  - Mais idiomas (ES, FR) — adicionar 1 JSON por idioma cobre.
